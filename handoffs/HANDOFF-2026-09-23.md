# Handoff v0.4.0: rota OptiScaler para jogos D3D12

23/09/2026. Leia depois de [HANDOFF-2026-09-20.md](HANDOFF-2026-09-20.md). Este arquivo cobre só a
rota nova.

---

## 1. O que entrou

No D3D12 o add-on do ReShade só enxerga o quadro pronto. Um jogo D3D12 com DLSS, FSR ou XeSS tem um
caminho melhor: o fork do OptiScaler
[neural-amd-opti](https://github.com/MatheusFerreiraS/neural-amd-opti), que assume a chamada do
upscaler do jogo e roda a mesma rede dentro dela, com a profundidade e os vetores de movimento do
próprio jogo. O instalador agora instala esse fork como mais uma rota.

| | |
|---|---|
| `Preset.OptiScaler` | rota x64, manifesto `"OptiScaler"`, último valor do enum (o `games.json` antigo continua lendo) |
| Recomendação | `GraphicsDetection.Preset`: jogo cuja melhor rota seria D3D12, ou que roda D3D11 e D3D12 e traz upscaler, recebe OptiScaler. `Recommended` vira D3D12, então um jogo com os dois ouve "troque para DX12" |
| Upscaler | `GraphicsDetector.Upscalers`: DLSS, FSR ou XeSS ao lado do exe, na raiz e, no Unreal, em `Plugins\` e `Engine\Plugins\` (uma passada por árvore) |
| Proxy | `dxgi.dll` ou `winmm.dll` (`Work.ProxyChoicesFor`) |
| Código | `src/AmdNr.Core/Work.OptiScaler.cs`: preflight, install e o que sobra depois do uninstall |

Nenhuma rota do ReShade sumiu. As duas coisas compartilham o manifesto x64, e é isso que as torna
alternativas: `Transaction.Apply` recusa um segundo preset na mesma pasta.

### O que vai para a pasta do jogo

`OptiScaler.dll` com o nome do proxy, `OptiScaler.ini`, `OptiScaler\` (FidelityFX, XeSS, XeLL),
`OptiScaler\D3D12_OptiScaler\D3D12Core.dll`, `experimental_lighting\`, o runtime **0.3.1** como
`dlssnr_amd_pass1.dll`, `pass2` e `pass3` (o OptiScaler carrega um módulo por passada) e os mesmos
weights do add-on. Todos os nomes estão em `Engine.Allowed`; `OptiScaler.ini` é configuração
(`Engine.IsConfig`), preservada no uninstall como o `ReShade.ini`, e um `OptiScaler.ini` que já estava
na pasta e não é nosso não é sobrescrito.

### Decisões que não são óbvias

- **O runtime não é o do add-on.** O `runtime` do payload é uma 0.3.0 com hash `70af3fb7…`, que o
  OptiScaler não reconhece (ele identifica o runtime por SHA-256 e usa offsets fixos). A rota usa a
  0.3.1 original do danielblnc (`b108d640…`), em componente próprio. Os weights são os mesmos
  (`6bf8dc93…`), então vêm do `runtime`.
- **`D3D12Core.dll` fica em `D3D12_OptiScaler/` no cache.** `PayloadManifest.Parse` recusa caminho com
  mais de dois níveis, e todo app já distribuído valida todos os componentes, inclusive os que não
  conhece. Um caminho de três níveis tornaria o manifesto ilegível para todo mundo. `Work.OptiDestination`
  põe o arquivo no lugar certo na hora de instalar.
- **Uninstall sem manifesto na rota OptiScaler não remove nada.** A varredura por nome da rota x64 tira
  `dlssnr_amd_pass1-10.dll` e os weights; numa pasta com um OptiScaler instalado por outro meio (o
  `Setup.bat` do pacote do fork) isso quebraria a instalação. Diz qual desinstalador usar.
- **Manifesto que sobrou de um uninstall do ReShade é adotado.** O uninstall do ReShade mantém o
  manifesto quando preserva o `ReShade.ini`, e `Apply` recusaria trocar de preset por cima dele para
  sempre. `AdoptLeftoverManifest` troca o preset quando só restam entradas de configuração.
- **`PayloadMovedOn` olha o preset.** Comparados com os pinos do add-on, `dlssnr_amd_pass1.dll` de uma
  instalação OptiScaler sempre pareceria desatualizado. `PinnedForOptiScaler` compara com os da rota.
- **Download sob demanda.** `PayloadManifest.OnDemand` e `Everyday`: os 132 MB do OptiScaler ficam fora
  do assistente, da aba "Esta máquina" e do "baixar tudo". Só descem quando alguém instala a rota.

## 2. Payload

Dois componentes novos no `payload.json`:

| componente | versão | de onde |
|---|---|---|
| `optiscaler` | `0.1.1-amd-nr` | o zip do release do neural-amd-opti no GitHub, com `extract` listando os 14 arquivos e o hash de cada um |
| `opti-runtime` | `0.3.1` | `dlssnr_amd_runtime-0.3.1.dll` no dataset do HF |

**Compatibilidade para trás:** o manifesto novo continua schema 1, com caminhos de no máximo dois
níveis, então um app antigo o lê. Mas o assistente de um app antigo baixa **todos** os componentes,
os 132 MB inclusive. Por isso a ordem continua sendo instalador primeiro, payload depois.

### Acoplamento com o neural-amd-opti: leia antes de publicar um OptiScaler novo

O payload pina o zip do release **e** cada arquivo extraído dele. Um release novo do fork é:

1. um componente `optiscaler` com versão nova (o cache é `<componente>/<versão>`);
2. a URL do zip do release novo;
3. os hashes do `extract` recalculados a partir desse zip.

O `publish-payload.ps1` não faz o passo 3: ele só sobe arquivos para o HF e deixa em paz o que tem URL
de outro host. Calcule os pinos do zip (nome, caminho, tamanho, SHA-256 de cada entrada) e edite o
`payload.json` antes de rodar o script. **Nunca re-suba um asset com o mesmo nome na mesma tag** do
fork: o endereço não muda e todo app passa a recusar o arquivo pelo hash.

## 4. O que ficou de fora

- Jogo **só D3D11** com DLSS continua recomendando o ReShade D3D11, que é a rota em que o add-on recebe
  profundidade e movimento. O OptiScaler também roda lá, pelas pontes D3D12 dele, mas não foi testado.
- A rota não tem seletor de versão do OptiScaler. A seção "Versão do add-on" some nela.
- O OptiScaler instala com o NR desligado (é o `OptiScaler.ini` do pacote). O relatório e a nota da
  rota dizem como ligar.

## 5. Release: o exe sozinho não basta

Sem `config.json`, `payload.json` e `api-db.json` na mesma pasta, o instalador não funciona. Todo
release leva, além dos dois arquivos soltos, um arquivo compactado com a pasta inteira:

| asset | para quê |
|---|---|
| `AMD-NR-ReShade-Installer.exe` | o atualizador automático baixa este (`Services.ExeAsset`); não pode sair do release |
| `SHA256SUMS.txt` | o hash que o atualizador confere (`Services.SumsAsset`) |
| `AMD-NR-ReShade-Installer-vX.Y.Z.7z` | o que a pessoa baixa na primeira vez: uma pasta com o exe, `config.json`, `payload.json` e `api-db.json` |

O `dotnet publish` já põe os três json em `publish-vX.Y.Z\` (vêm de `src/AmdNr.App/config.json`
e de `payload/`). Como o instalador sai antes do payload, depois do `publish-payload.ps1` copie
`payload/payload.json` de novo para essa pasta e só então compacte, para o arquivo que vai junto
ter os componentes novos. O atualizador só troca o exe, então quem já tem a pasta continua com os
json dela.

O `.7z` da v0.4.0 foi montado à mão com os json e o `LEIA-ME.txt` do beta de 15/09. O `config.json`
aponta para o HF, então online ele lê o manifesto atual; o `payload.json` de lá (sem `optiscaler`)
só seria usado sem internet.
