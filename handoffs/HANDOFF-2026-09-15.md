## 1. O que é

`AMD-NR-ReShade-Installer` é o gerenciador gráfico do add-on
[dlss5-neural-amd](https://github.com/zmodelerlover/dlss5-neural-amd), que roda a rede de Neural
Rendering do DLSS 5 em placas Radeon através do ReShade.

Ele resolve as duas coisas que o installer de terminal não resolvia:

- os arquivos vinham do canal `files` do Discord, e achar aquilo era onde a maioria travava;
- era um terminal: não mostrava biblioteca, não detectava GPU, não avisava de versão nova.

Hoje ele **instala tudo sozinho, sem nenhuma janela de terceiros**: add-on, runtime, pesos, o par
do bridge 32-bit e **o próprio ReShade**.

- Repositório: `D:\AMD-NR-ReShade-Installer` (git, branch `master`, ainda **não publicado**).
- Executável publicado: `D:\AMD-NR-ReShade-Installer\dist\AMD-NR-ReShade-Installer.exe`
  (~48 MB, self-contained, não precisa de .NET instalado).
- Dados do usuário: `%AppData%\AmdNrInstaller\` (`cache\`, `logs\`, `games.json`, `settings.json`).

## 2. Decisões já tomadas (não reabrir sem motivo novo)

| Decisão | Por quê |
|---|---|
| **Tudo em C#**, porte do motor Rust | Escolha do usuário. O Rust (`installer/` do outro repo) continua existindo e não foi tocado. |
| .NET 10 + Avalonia 11.3.12, sem framework de MVVM | Mesma pilha do Optiscaler-Client, que é a referência de UX. |
| **Update = checar e avisar**, nunca auto-substituir | O Optiscaler-Client removeu o auto-update em 18/08/2026: com `PublishSingleFile` o Windows trava o exe e o app voltava rodando a build velha. |
| Payloads num **dataset do Hugging Face** | Os arquivos não podem estar no GitHub, e o usuário **troca payload com frequência**. HF é o único host grátis cujo endereço é ao mesmo tempo **estável e sobrescrevível**: `https://huggingface.co/datasets/<user>/<repo>/resolve/main/<arquivo>` continua o mesmo depois de subir build novo. Logo trocar payload nunca mais exige build novo do app. Leitura é anônima (repo público, app não manda token), serve `Range` (conferido: `206` num LFS de 548 MB), e é feito pra peso de modelo — 141 MB é nada lá. Conta só com e-mail, sem cartão. |
| **catbox.moe vira mirror** | Foi o primeiro destino (upload sem conta nenhuma, o mais anônimo que existe) e funciona: os 9 arquivos foram conferidos byte a byte de lá. Mas endereço de catbox é **imutável** — payload novo = URL nova = `config.json` novo = build novo. Custo que não paga. Fica como segundo endereço, grátis, e nada é confiado além do hash. |
| `mirrors[]` por arquivo | Endereços extras por arquivo, tentados em ordem. Trocar ou somar host vira edição do manifesto, não build novo. |
| **Base de APIs distribuída** (`payload/api-db.json`), não consulta ao vivo | Medido: depois de ~40 consultas o Cloudflare do PCGamingWiki passou a responder **403 para o .NET** enquanto o curl do mesmo IP passava. Consulta ao vivo do PC de cada usuário não funcionaria em escala. |
| **ReShade extraído do instalador oficial**, não executado | O `.exe` do ReShade é um zip anexado. Extrair dá install silencioso, com backup e desinstalação pelo mesmo motor transacional. Rodar o setup escondido não dá nada disso. |
| Código do Optiscaler-Client **não é reaproveitado** | Ele é GPL-3.0, este repo é MIT. Só o *método* foi copiado (quais chaves de registro varrer, `Binaries\Win64`, fingerprints de DLL). |

## 3. Arquitetura

```
src/AmdNr.Core/     net10.0-windows, sem dependências externas
  Engine.cs         hashes, PE, INI, ownership, paths, MoveFileEx write-through
  Manifest.cs       o manifesto de install (formato byte-a-byte compatível com o C++/Rust)
  Transaction.cs    guard + apply + uninstall (journal, backup, rollback)
  X86Installer.cs   rota 32-bit (bridge)
  Work.cs           presets, Report, preflight, install, uninstall, detect
  Graphics.cs       qual API o jogo usa: imports do exe, engine, fingerprints
  Pcgw.cs           parser do template {{API}} do PCGamingWiki + normalização de título
  ApiDatabase.cs    api-db.json: leitura, lookup por appid e por título
  Scanning.cs       Steam/Epic/GOG/EA/Ubisoft/Battle.net/Xbox
  PayloadManifest / PayloadCache / CoverCache   download, extração, verificação, staging

src/AmdNr.App/      net10.0-windows, Avalonia, single-file self-contained win-x64
tests/AmdNr.Core.Tests/   117 testes
tools/ApiDbBuilder/       gera payload/api-db.json a partir do PCGamingWiki
tools/seed-cache.ps1      enche o cache a partir de arquivos locais (offline / teste)
payload/payload.json      o que baixar, de onde, e qual hash
payload/api-db.json       840 jogos: quais APIs cada um suporta
```

O motor foi portado de `installer/src/engine.rs` e `installer/src/work.rs` do outro repositório.
**Comportamento é contrato**: as frases de recusa são asseridas por teste e o manifesto de install
tem que continuar byte-a-byte igual ao que o instalador C++ escrevia, senão toda instalação já
existente vira "Modified or unsupported install manifest".

## 7. Armadilhas já pagas (não repetir)

- **Cloudflare bloqueia o HttpClient do .NET por impressão TLS.** Cabeçalhos e versão de HTTP não
  mudam nada; o curl do Windows passa. Por isso o `ApiDbBuilder` chama `curl.exe` por processo, e
  por isso a base é distribuída em vez de consultada.
- **`ZipArchive` não abre zip anexado a exe**: os offsets contam do início do zip. Achar o EOCD e
  rebasear (`PayloadCache.OpenAppendedZip`).
- **Regex de campo de template**: `\s*` engole a quebra de linha, então campo vazio rouba a linha
  seguinte como valor. Foi assim que Metro 2033 "suportava" Vulkan e OpenGL. Use `[ \t]*`.
- **O nome do arquivo não diz o que o DLL é.** O `dxgi.dll` do God of War aqui é OptiScaler. Ler
  o recurso de versão antes de dizer "ReShade encontrado".
- **Jogo Unreal**: o add-on vai em `<Projeto>\Binaries\Win64`, não na raiz — a raiz só tem o stub.
- **Jogo com nome em algarismo romano**: "Grand Theft Auto V" → `GTA5.exe`. A escolha do exe
  normaliza romano para dígito, e exclui `*LanguageSelect*`, `*trial*`, crash handlers etc.
- **`$Home` é variável reservada do PowerShell**; e parâmetro `[string]$X` converte objeto em
  string silenciosamente (foi assim que o `seed-cache.ps1` "não achou componente nenhum").
- **Heredoc de Python com `\a`, `\n`, `\\`** estraga caminho e string de C#. Preferir edição direta.
- **A rota 32-bit não instala o `addon64`** e lê os payloads tanto de `files\` quanto da raiz do
  staging.

## 10. O que mudou em 15/09 (segunda passada)

### Bug reportado: Desinstalar não apagava o "Instalado"

Causa raiz em `Scanning.cs`. `IsInstalled` respondia pela **existência do manifesto**:

```csharp
File.Exists(.../dlss5-neural.install.json) || File.Exists(.../dlss5-x86bridge.install.json) || ...
```

Só que `Transaction.Uninstall` **guarda o manifesto de propósito** sempre que preserva uma entrada
de configuração — e um install de 64-bit **sempre** escreve `ReShade.ini` como entrada owned+config.
Logo todo uninstall bem-sucedido deixava o manifesto, e o badge nunca apagava. Os arquivos eram
removidos corretamente o tempo todo; o que mentia era a leitura do estado.

Agora o estado vem dos payloads em disco (`Work.InstalledMarkers`), que é exatamente o conjunto que
o uninstall retira. Provado nos dois níveis: os testes falham contra o código antigo, e a UI
headless mostra `badge=True -> False` com `manifesto=True` nos dois lados.

### Primeiro uso

`SetupWindow` — janela separada, 4 passos: idioma, esta máquina (GPU + HIP 7), arquivos (confere o
hash de cada componente e baixa o que falta), seus jogos (scan). Grava em `settings.json`,
`games.json` e no cache, que é o que a janela principal já lê, então não devolve nada além de
"chegou ao fim". Fechar no X **não** marca `SetupDone`, e na próxima abertura ele pergunta de novo.
`App.OnFrameworkInitializationCompleted` troca `ShutdownMode` enquanto o wizard está aberto, senão o
processo morreria ao fechá-lo (não há MainWindow ainda).

### Logo

`Assets/logo.png` (recorte quadrado e centrado do PNG do usuário, que tem alpha) e `Assets/app.ico`
(16 a 256, gerado dele). Tile de fundo virou **branco** (`LogoFill`) porque o logo é vermelho:
vermelho sobre vermelho não lê a 40px. Dois lugares usam: o rail e o card "Sobre" em Configurações.

### Bugs de UI achados no render headless

1. `Border.iconTile.ok > PathIcon` era seletor de **filho direto**, e os tiles que também mostram
   spinner embrulham o ícone num `Panel`. Resultado: fundo ficava verde, ícone continuava branco.
   Afetava o banner de resultado da folha e o passo "Arquivos". Virou seletor de descendente.
2. Tamanho de componente com divisão inteira: tudo abaixo de 1 MB aparecia como "0 MB".
3. O card "Sobre" tinha o "NR" em texto e ficou como quadrado branco vazio depois da troca do logo.

### Bugs de core achados no review

4. **Três `async void` sem `catch`** (`OnInstall`, `OnUninstall`, `OnScan`). O motor embrulha o que
   prevê em `InstallException`, mas o que escapar matava a janela no meio de um install. Agora vira
   linha de relatório (`Failure(ex)`) e vai pro log.
5. **`ScanAll` só tratava três tipos por fonte.** Um `.vdf`/registro em formato inesperado virava
   `AggregateException` do `Parallel.ForEach` e derrubava o app. Agora uma fonte que falha custa os
   jogos dela, nunca a varredura nem a janela.
6. **Uninstall 32-bit sem manifesto dava erro vermelho** ("No install manifest") para a situação
   normal de uma pasta onde nada foi instalado. O 64-bit sempre varreu por nome nesse caso. Agora os
   dois fazem igual.
7. **`Pins()` sem manifesto cai para `AddonSize = 0`**, e o preflight comparava o arquivo certo
   contra esse zero: *"isto é 550400 bytes, e este release espera 0. That is a different build"*.
   Tamanho desconhecido agora não é comparado.

### Hospedagem

Duas passadas. Primeiro catbox.moe (upload sem conta, o mais anônimo possível): os 9 arquivos, mais
`payload.json` e `api-db.json`, subiram e foram baixados de volta e conferidos contra o hash pinado.
Funciona — mas endereço de catbox é **imutável**, e o usuário troca payload com frequência, então
cada troca custaria um build novo do app.

Destino final: **dataset do Hugging Face**, endereço estável e sobrescrevível. `tools\publish-payload.ps1`
faz a migração e toda troca futura num comando: sobe o que mudou, recalcula tamanho e SHA-256 dos
bytes locais, **incrementa a versão do componente que mudou** (o cache é `<componente>/<versão>`, e
bytes novos sob versão igual leem como cache corrompido), reescreve e sobe o `payload.json`, e então
baixa tudo de volta pra conferir. `-Verify` sozinho só confere. Os endereços do catbox ficam como
`mirrors`.

O `dlss5-neural-host64.exe` está no catbox sob endereço `.bin` porque o catbox recusa `.exe` — não
custa nada, porque `name` é o nome em disco e `url` é só de onde vêm os bytes. No HF isso não é
necessário.

**Publicado em `zmodelerlover/amd-nr`** (dataset público). Os 8 arquivos mais os dois manifestos,
todos baixados de volta e reconferidos. O fallback de mirror foi exercitado de verdade: endereço
primário morto cai no mirror do catbox e passa no hash, e mirror com outros bytes é recusado.
Prova de ponta a ponta com cache zerado: o código do próprio app baixou tudo do endereço estável e
montou o staging das duas rotas; `api-db` com 840 jogos.

**O token de write usado na publicação foi colado no chat — revogar em
huggingface.co/settings/tokens.** O login já está salvo em `~/.cache/huggingface/`, então revogar
não quebra nada até a próxima publicação, que vai pedir `hf auth login` de novo.

### Testes

120 verdes (eram 117). Os novos: manifesto preservado não é install; round-trip x64 com ReShade
apaga o badge; uninstall x86 sem manifesto varre em vez de falhar; tamanho desconhecido não vira

## 11. Terceira passada: emuladores, Play, log por instalação

### Emuladores agora são um caminho, não só uma rota

`src/AmdNr.Core/Emulators.cs` — tabela de 14 emuladores: como reconhecer (nomes de exe), qual rota,
quais renderizadores, e **a frase que nomeia o ajuste que realmente decide**. Botão "Emulador…" na
barra: escolhe PCSX2, RPCS3 ou "outro", e então pede a pasta *daquele* emulador. O que está na pasta
manda — quem escolher PCSX2 e apontar o RPCS3 recebe RPCS3, não uma rota errada em silêncio.

**Bug de core que isso desenterrou:** `GuessPreset` acertava PCSX2/RPCS3, e `DetectAllAsync`
**sobrescrevia** com `Dx11` logo em seguida, porque a detecção não sabia o que era emulador e o exe
de um emulador importa todos os renderizadores de uma vez. A rota de emulador nunca sobrevivia.
Agora `Emulators.Identify` é o sinal 0 da detecção, antes de qualquer leitura de import, e
`GuessPreset`/`ExpectedExe`/`CheckExe` leem a mesma tabela — não dá mais pra discordarem.

`CheckExe` também aceita qualquer nome de build do mesmo emulador (o PCSX2 sai sob cinco).

### Play / Abrir na folha

Steam vai por `steam://rungameid/<appid>` — é o caminho que o jogo espera (launcher próprio, DRM,
overlay); rodar o exe direto quebra isso. Sem appid, o executável que a detecção já achou. Rótulo
vira "Abrir" quando é emulador, e o botão desliga quando não há o que abrir.

### Log por instalação

`%AppData%\AmdNrInstaller\logs\<data>-<ação>-<jogo>.log`, um por install/uninstall, mantendo os 100
mais novos. Carrega o que um relato de bug precisa e o relatório na tela não tem: máquina (GPU,
driver, HIP 7), alvo e rota **e quem escolheu a rota**, a evidência da detecção, versões e hashes
dos payloads, o relatório inteiro, e a pasta depois — com cada DLL identificada pelo recurso de
versão, não pelo nome (`dxgi.dll [ReShade 6.8.0]`).

### Half-Life: por que o ReShade não abriu

Não era o instalador. O `d3d9.dll` na pasta tem hash idêntico ao ReShade32 pinado — foi instalado
certo. O que acontece é que o `hw.dll` do Half-Life importa **só `OPENGL32.dll`**: a build atual da
Steam não tem renderizador Direct3D nenhum, então nada nunca carrega aquele `d3d9.dll`.

A detecção pelos arquivos acerta sozinha (diz OpenGL, rota nenhuma). Quem forçou D3D9 foi o
`api-db`: o PCGamingWiki lista D3D9 (verdade na build pré-aniversário) e o `With(wiki)` **substitui**
o que os arquivos dizem. Não virou lista de exceções — o projeto recusa whitelist. Virou
`CheckRouteIsReachable`: quando a rota pede um renderizador que os arquivos desta cópia não linkam,
o preflight avisa, com a evidência. Half-Life agora diz:

> This route needs DX9, and the files here link OpenGL instead. hl.exe loads hw.dll, which imports
> opengl32.dll.

**Half-Life não tem como funcionar nesta build.** O aviso é o produto, não uma correção.

### Mais um bug de core, achado na mesma saída

`CheckReShade` só procurava nomes de 64-bit (`d3d11/dxgi/d3d12`). Na rota 32-bit D3D9/D3D8 o ReShade
entra como `d3d9.dll`, então **toda** instalação 32-bit recebia "No ReShade proxy DLL found here"
com o ReShade ali na pasta — inclusive as que o próprio app tinha acabado de escrever. Os nomes
agora seguem a rota.

### Source: a raiz é stub, o renderizador vive em bin
**CONFIRMADO EM JOGO em 15/09.** O usuário rodou o Half-Life 2 depois da correção e funcionou. O log
do ReShade prova a cadeia inteira:

```
Searching for add-ons (*.addon, *.addon32) in '...\half-life 2in' ...
Loading add-on from '...\half-life 2in\dlss5-neural.addon32' ...
Registered add-on "dlss5 neural x86 bridge" v0.0.0.0 using ReShade API version 20
```


Reportado como "no Half-Life 2 não deu certo instalar". A instalação estava **correta** e no lugar
errado. O log por instalação entregou de primeira: rota `X86Dx9`, `d3d9.dll [ReShade 6.8.0]`, tudo
conferido — na raiz.

Lendo os binários:

| módulo | arch | importa |
|---|---|---|
| `hl2.exe` (raiz) | x86 | **nada de gráficos** — stub |
| `bin\shaderapidx9.dll` | x86 | **`d3d9.dll`** |
| `bin\shaderapivk.dll` | x86 | `DXVK_D3D9.DLL` |

O Source carrega os módulos de `bin\` com `LOAD_WITH_ALTERED_SEARCH_PATH`, então as dependências
deles resolvem a partir de `bin\` e **a raiz nunca é consultada**. Provado em duas etapas: com o
ReShade só na raiz não existia `ReShade.log` em lugar nenhum; copiado para `bin\`, ele carregou e
logou `Searching for add-ons (*.addon, *.addon32) in '...\Half-Life 2\bin'` — o add-on continuava na
raiz, e por isso a aba não aparecia.

**A correção separa dois conceitos que estavam colados:** `GraphicsDetection.Executable` é o que se
abre (continua `hl2.exe`), e o novo `InstallTarget` é o arquivo cuja pasta recebe os arquivos
(`bin\shaderapidx9.dll`). `Target` devolve um ou outro; `TargetFor` e `RefreshInstalled` usam
`Target`. Um jogo comum tem `InstallTarget` nulo e nada muda para ele.

Nota: o backend "Vulkan" do Source é DXVK traduzindo D3D9, então a rota D3D9 serve aos dois.

É a mesma forma do Unreal (`Binaries\Win64`), que já era tratada — mas por um caminho diferente
(`FindExecutable` achava o exe certo). Source não dava para resolver assim, porque o exe certo está
na raiz e os arquivos não.

## 12. Roadmap

### Escolher a release/versão por jogo, na folha

Hoje a versão é global: `payload.json` dá **uma** `version` por componente e todo jogo instala
aquela. O pedido é que, ao clicar no jogo, a pessoa escolha qual release quer — **da 0.5 em
diante** (nada anterior entra na lista).

Serve para duas coisas que já aconteceram neste projeto: testar uma runtime nova em um jogo só sem
mexer nos outros, e voltar um jogo para a versão anterior quando a nova regride nele.

**O que isso toca, em ordem de dificuldade:**

1. **`payload/payload.json`** — hoje `components.<nome>.version` é uma string. Vira uma lista de
   versões, cada uma com os seus `files` (url, size, sha256). O `schema` sobe de 1 para 2, e o
   `PayloadManifest.Parse` tem que continuar aceitando o schema 1 — senão todo exe já distribuído
   deixa de ler o manifesto no próximo publish.
2. **`GameEntry`** (`src/AmdNr.App/Services.cs`) — ganha algo como `PayloadVersion`, nulo = "a mais
   nova". Mesmo padrão do `PresetChosen`: uma vez escolhida à mão, a atualização do manifesto não
   sobrescreve mais.
3. **A folha** (`MainWindow.axaml`) — uma combo ao lado da de Rota. Só aparece quando há mais de uma
   versão oferecida.
4. **`PayloadManifest.Pins()`** — hoje devolve os hashes da única versão. Passa a receber qual.
5. **`tools/publish-payload.ps1`** — em vez de sobrescrever a versão, acrescenta uma entrada na
   lista. Isso muda o `-SetVersion` e o auto-bump.

**O que NÃO precisa mudar, e é o que torna isso barato:** o cache já é
`cache\<componente>\<versão>\` e o staging já é `<componente>.<versão>-...`, então duas versões
convivem em disco sem nenhum trabalho novo. O `Transaction` já grava no manifesto do jogo o que foi
instalado, e o preflight já confere hash por hash.

**Armadilha a não repetir:** o endereço do Hugging Face é estável *por nome de arquivo*. Publicar
uma 0.6 sem mudar o nome sobrescreve a 0.5 e a lista passa a mentir. Versões que coexistem precisam
de nomes que coexistem — `dlssnr_amd_pass1-0.2.18.dll`, não `dlssnr_amd_pass1.dll` de novo.

### Aberto: dois bugs no `dlss5-neural.ini` da rota 32-bit

Achados conferindo o hotkey contra o binário do add-on, não corrigidos.

1. **`Engine.FreshIni()` escreve `ColourStrength=0.25`, e essa chave não existe no add-on.** Zero
   ocorrências no binário, nem como linha de ini nem como substring; `ColorStrength` também zero.
   Não é variante de grafia, é configuração morta. As outras quatro (`Scale`, `Passes`, `Structure`,
   `Skin`) existem.
2. **O ini pré-escrito engole o template documentado do add-on.** O add-on só escreve o dele
   *"because no dlss5-neural.ini was here"*; a rota 32-bit escreve um primeiro, então o arquivo que
   sobra não tem `StartOn`, nem `ToggleKey`, nem `ToggleMods`, nem o bloco que explica os códigos de
   tecla. E o próprio instalador manda setar `StartOn=1` nesse arquivo — que numa instalação 32-bit
   não tem essa linha. O hotkey continua funcionando (Ctrl+End vem do default compilado); o que se
   perde é descobrir e trocar ele pelo caminho documentado. A rota 64-bit não escreve o ini e não
   tem o problema.

O hotkey em si está certo: o add-on define `ToggleKey=35` (0x23 = VK_END) e `ToggleMods=1` (Ctrl),
então **Ctrl+End** e `StartOn=1` conferem com o que o instalador diz.

Conserto proposto: parar de pré-escrever o ini na rota 32-bit e tirar o `ColourStrength`. Conferir
antes no Rust original (`git -C D:\dlss5 show origin/master:installer/src/work.rs`) se havia motivo
para esses valores — `Scale=1.0` e `Passes=1` são idênticos aos defaults do add-on, então os únicos
"overrides" reais hoje seriam `Structure=1` e `Skin=1`, se é que diferem.


### Hotkey: diagnosticado — o ini é lido, o overlay não salva

Relatado pelo usuário, **não reproduzido e não diagnosticado**. Fica aqui com o que já se sabe, para
a investigação não começar do zero.

O que foi conferido em 15/09, no Half-Life 2 (rota 32-bit, instalado em `bin\`):

| | |
|---|---|
| `Half-Life 2\dlss5-neural.ini` | 147 bytes, 04:01:59 — sem `ToggleKey`/`ToggleMods`/`StartOn` |
| `Half-Life 2\bin\dlss5-neural.ini` | 147 bytes, 04:06:10 — idem |
| atributos | `A` nos dois; nenhum é somente-leitura |

147 bytes é exatamente o que `Engine.FreshIni()` escreve. Ou seja: **nenhum dos dois foi escrito pelo
add-on até agora.** O overlay do add-on salva em `dlss5-neural.ini` e nada chegou lá.

**RESOLVIDO em 15/09, com o add-on rodando no Half-Life 2.** Duas metades, e só uma está quebrada.

**O ini é lido.** Escrevendo `ToggleKey=120` e `ToggleMods=1` à mão em `bin\dlss5-neural.ini` e
reiniciando o jogo, o log do bridge confirma que ele pegou:

```
x86bridge native x86 protocol=2 mode=NEURAL StartOn=0 ToggleKey=120 ToggleMods=1 probe=off
```

Esse log é a ferramenta de diagnóstico: **o add-on imprime o bind em uso na inicialização**, então dá
para saber o que ele está rodando sem ver a tela.

**O overlay não salva.** Varredura da árvore inteira do HL2 durante uma sessão de 5 minutos com o
add-on carregado e registrado: nenhum `dlss5-neural.ini` foi escrito, nem em `bin\` nem na raiz. O
add-on criou os logs dele e mais nada. O Save do painel não persiste a tecla.

**Portanto:** dá para trocar o hotkey editando o arquivo; não dá pelo painel. É bug do add-on
(outro repositório), não do instalador.

**O que ainda não se sabe:** se a captura da tecla no painel não registra a combinação, ou se
registra e o Save é que não escreve. De fora não dá para separar.

**Contexto que pode importar para quem for atacar isso:**

- O jogo estava em **tela cheia exclusiva** (`Windowed | FALSE` no ReShade.log). Teste barato e
  óbvio: repetir em janela. Se a captura funcionar em janela, é problema de input em exclusivo.
- Source usa SDL2 e cria uma janela separada só para input (`SDLHelperWindowInputCatcher` aparece no
  ReShade.log). Se o add-on lê teclado por um caminho ligado à janela de render, pode nunca ver a
  tecla. O overlay do ReShade em si responde normalmente, então o caminho do ReShade funciona.
- ReShade instala hooks em `dinput.dll` e `dinput8.dll`.

**Armadilha ao testar:** não usar **F10**. No Windows F10 gera `WM_SYSKEYDOWN`, não `WM_KEYDOWN`, e
um handler que só escuta `WM_KEYDOWN` nunca dispara — um falso negativo que não tem nada a ver com o
bug. Usar F9 (120) ou Insert (45).
