# Handoff — v0.2.0: instalar em jogo OpenGL, e o payload que quase saiu quebrado

20/09/2026. Tudo empurrado e publicado: instalador `v0.2.0`, add-on `v0.6.0`, payload com o
`addon` em 0.6.0. Leia depois de [HANDOFF-2026-09-15.md](HANDOFF-2026-09-15.md), que continua
sendo a descrição completa do app; este arquivo cobre só o que mudou e o que deu errado.

---

## 1. O que entrou

O add-on ganhou rota de OpenGL, então o instalador ganhou como instalá-la.

| | |
|---|---|
| `Preset.OpenGL` | rota x64, na ordem de preferência **depois** do Vulkan |
| Proxy | `opengl32.dll`, com `dinput8.dll` como alternativa |
| Detecção | `(X64, GraphicsApi.OpenGL) → Preset.OpenGL`; 32 bits continua sem rota |
| Manifesto | `"OpenGL"` aceito em `Manifest.Decode` |
| Emuladores | xemu deixa de ser beco sem saída; melonDS ganha instrução de renderer; Azahar mantém Vulkan como recomendação |

O nome do proxy não foi chutado. A lista de nomes em `Work.ProxyChoicesFor` diz, no próprio
comentário, que são os nomes cujos entry points o ReShade fixado realmente exporta — então li os
exports do `ReShade64.dll` pinado: 24 entradas `wgl*` mais o conjunto GL 1.1. `opengl32.dll` passa
pelo mesmo critério que `dxgi.dll` e `dinput8.dll` passaram.

Validado fora dos fixtures: apontando `GraphicsDetector.Detect` para a pasta real do Luanti, a
resposta é `luanti.exe imports opengl32.dll → api OpenGL → preset OpenGL → opengl32.dll`.

### O bug que o teste pegou antes do usuário

`Manifest.Decode` valida o nome da rota contra uma lista fechada, e `"OpenGL"` não estava nela. A
instalação teria **gravado** o manifesto e a leitura seguinte o recusaria — levando junto o estado
da pasta e o desinstalar. É o tipo de defeito que só aparece depois de escrever no disco de
alguém. Acrescentar nome ali é compatível para trás: manifesto antigo continua decodificando, e um
build antigo recusa um manifesto novo, que é a resposta honesta, porque ele não teria rota para
desinstalar.

## 2. O incidente do payload — leia antes de publicar qualquer coisa

**As duas cópias do `payload.json` estavam dessincronizadas.** A deste repositório
(`payload/payload.json`) ainda pinava o `bridge` em **v0.5.2**, enquanto os arquivos publicados
sob aqueles nomes são o par **v0.5.3**. A cópia espelhada no repositório `AMD-NR-Extras` estava
certa. Ninguém tinha como notar, e a razão é o item 3 abaixo.

Publicando a partir da cópia deste repositório, os hashes velhos do bridge foram para o manifesto
ao vivo. Durante alguns minutos, **uma instalação em jogo 32 bits teria sido recusada na
conferência de hash** — o app faz exatamente o que deve fazer, e o manifesto é que estava errado.

Corrigido pegando os pins do `extras` (que são os dos arquivos realmente publicados), republicando
e rodando a verificação completa, que agora passa nos nove arquivos. As duas cópias estão
idênticas e commitadas.

**A regra que fica:** antes de publicar, compare `payload/payload.json` com o do `AMD-NR-Extras`.
Se divergirem, descubra qual descreve o que está no dataset **antes** de subir — `publish-payload.ps1
-Verify` responde isso sem escrever nada.

---

## 3. Por que o script deixava isso passar

`tools/publish-payload.ps1` morria **entre subir o manifesto e verificá-lo** — o pior lugar
possível: tudo no ar, nada conferido. Causa: o `hf` escreve avisos no stderr (`Removing 1 file(s)
from commit that have not changed`) e, sob `ErrorActionPreference = 'Stop'`, uma linha de stderr
redirecionada vira erro terminante no Windows PowerShell.

Agora todas as chamadas passam por `Invoke-Hf`, que relaxa a preferência durante a chamada e deixa
o veredito com o código de saída — que todos os chamadores já testavam. O passo 7 do script (baixar
tudo de volta e conferir hash) volta a rodar, e foi ele que pegou o problema do item 2.

Duas armadilhas encontradas ao escrever isso, ambas no comentário do código:

- a função **não** pode se chamar `Hf`: o PowerShell não diferencia maiúsculas, o nome sombreia o
  executável `hf` e a chamada de dentro re-entra na função;
- rodar o script pelo Git Bash embaralha o `PSModulePath`, e aí cmdlets como `Get-FileHash` somem.
  Rode pelo PowerShell. Isso não é bug do script — cheguei a "corrigi-lo" com base nesse
  diagnóstico errado e revertí.

## 4. Estado publicado

| | versão | onde |
|---|---|---|
| Instalador | `v0.2.0` | release com `AMD-NR-ReShade-Installer.exe` + `SHA256SUMS.txt` |
| Add-on | `v0.6.0` | release com `dlss5-neural.addon64` + `SHA256SUMS.txt` |
| Payload | `addon` 0.6.0, `runtime` 0.3.0, `reshade` 6.8.0, `bridge` 0.5.3, `x86-extras` 1 | dataset `zmodelerlover/amd-nr` |

`publish-payload.ps1 -Verify` passa nos nove arquivos.

**O auto-update foi testado pelo usuário depois da publicação e funcionou** — a 0.1.1 se trocou
pela 0.2.0 sozinha. Era o caminho que nunca tinha sido exercitado de ponta a ponta: o release
publica o par `.exe` + `SHA256SUMS.txt`, o app baixa, confere o hash contra o sums do mesmo
release, move o executável em uso para `.old`, põe o novo no lugar e reinicia.

Ordem de publicação, que importa: **instalador primeiro, payload depois**. O `payload.json` é lido
em tempo de execução por todo instalador já instalado, então no instante em que o add-on novo
entra no manifesto, quem está na versão antiga passa a baixá-lo — funciona nas rotas que aquela
versão conhece, mas ela não oferece a de OpenGL.

## 5. O que ficou de fora

- `GameScanner.GuessPreset` continua chutando `Dx11` antes da detecção rodar. É comportamento
  antigo e inofensivo — a detecção sobrescreve logo depois, e o cartão assenta em OpenGL sozinho —
  mas duplica conhecimento que já existe em `GraphicsDetection.RouteFor`.
- O script reescreve `src/AmdNr.App/config.json` com BOM e indentação própria a cada publicação,
  sem mudar conteúdo. `File.ReadAllText` engole o BOM, então é só ruído de diff; foi revertido à
  mão nesta publicação.
- Nada no app diz que uma rota é experimental além do texto da nota. A de OpenGL é a mais nova de
  todas.
